03

5 Data Moving Patterns (Shape)

Migration1

One-way; one-to-one; one time. Transfer of data in one direction, from one system to another, in a single discrete session. Three parts: filtering criteria, transformation, and verification checks. Keeps you from being locked into a vendor — without it you'd lose acquired data if you were unable to move it. Built to handle enormous volumes and process a large number of records in parallel. There are no second chances — once off, it's permanent.

Broadcast2

One-way; one-to-many; continuous. Constant transmission of data from a single source to multiple destinations. It is transactional — applies only to data that has moved since the last time it moved, never the whole dataset. Initiated either by an event or on a timetable.

Bi-Directional Sync3

Two-way; two systems; continuous. Process of combining two datasets from two separate systems; each exists independently. Performs in unison to ensure both sides have an accurate, up-to-date view. It is the only pattern in which two systems can disagree — a conflict arises if both change the same record at the same moment, and something has to decide who wins.

Correlation4

Two-way; two systems; continuous. Similar to bi-directional sync, except carried out only on data that is pertinent to both systems. Performs sync at the intersection of two datasets and never creates new records. Includes a filter — only records that exist in both. Simpler, faster, and more time-efficient than bi-directional sync.

Aggregation5

Centralized view of real-time data from numerous systems. Merges multiple systems into a single system; data is retrieved, merged, and transformed. Implemented using ETL or ELT, feeding a data warehouse.

05

7 System Wiring Patterns

Point-to-Point

Individual systems connect directly to one another, no mediator or hub. Direct integration via custom interfaces built from scratch. Tight coupling — a change in one system forces changes in the one it's connected to. Simple to implement. Connections = N × (N-1) / 2. Example: a retailer integrating its website with PayPal, Stripe, and Braintree.

Hub-and-Spoke

Numerous systems connect to a central integration hub (middleware). Indirect communication — systems talk through the hub, which provides decoupling. Scales well and routes communications correctly, but the hub is a single point of failure. Example: an ESB linking a storefront, inventory, and order fulfillment.

Request-Response

Synchronous communication — one system makes a request and waits for the other to respond. A blocking operation: the requester stops processing until the answer or timeout arrives. Used for HTTP APIs, web services, client-server apps. Weakness: timeout settings and error handling. Example: a shopping system requests a payment server to process payment.

Publish-Subscribe (Pub/Sub)

Asynchronous, event-driven communication through a message broker. Messages go to topics/channels; subscribers get them when available. Several subscribers can consume simultaneously. Uses brokers like Apache Kafka or RabbitMQ. Benefit: real-time, loosely-tied communication. Weakness: broker availability. Example: fleet management publishes to a topic; subscribers get real-time updates.

File-Based

Systems generate or consume files exchanged asynchronously — no direct or real-time communication. Files use a conventional or custom format (CSV, XML). Needs data transformation: mapping, validation, enrichment. Best for batch processing and older systems — not for real-time needs, large volumes, or when speed doesn't matter. Weaknesses: error handling, data consistency, monitoring, error recovery. Example: HR drops an employee CSV into a shared network directory.

Real-Time (Near Real-Time)

Instantaneous movement of data and communication — within milliseconds or seconds. Event-driven, with a continuous, uninterrupted data flow. High throughput, low latency. Used in IoT, trading platforms, financial and real-time analytics. Weakness: needs scalability, event processing, and data consistency. Example: placing an order generates an event uploaded to the integration platform instantly.

Hybrid

Combines traditional and modern methods in the most effective way to meet requirements — see the four combinations in the section below.

06

4 Hybrid Integration Combinations

1Point-to-Point + Message Queuing — P2P handles immediate request-response; MQ handles asynchronous, reliable communication
2Hub-and-Spoke + Pub/Sub — the hub makes point-to-point connections possible; pub/sub enables event-driven communication; one piece of middleware, two behaviors
3File-Based + Real-Time — File-Based handles bulk/historical data on a schedule; Real-Time handles events acted on immediately
4SOA + Microservices — coarse-grained reusable services (SOA) coexist with fine-grained, independent microservices; often a migration path as older services are broken apart over time

SOA

Emerged from the late 1990s to the 2000s. Associated standards: SOAP, WSDL, UDDI.

Microservices

Popularized around 2011–2014.

07

Comparison Tables

Point-to-Point

  • Grows very fast
  • Tight coupling
  • Links in every system
  • Simple, direct, quick
  • Unmanageable with many systems
  • No middleware
vs

Hub-and-Spoke

  • One hub per system
  • Loose coupling
  • Links to hub only
  • Scales, decouples, centralized
  • Single point of failure
  • ESB or integration hub

Request-Response

  • Synchronous
  • Sender waits
  • No middleware
  • Sender knows receiver
  • Adding a receiver requires changing center
  • HTTP APIs, web services
  • Risk is latency and timeouts
vs

Pub/Sub

  • Asynchronous
  • Publishes and moves on
  • Has message broker
  • Sender only knows topic
  • Subscribe only; sender unchanged
  • Apache Kafka, RabbitMQ
  • Broker becomes a weak point

File-Based

  • On a schedule, in batches
  • Systems share a folder
  • Large volumes, legacy systems, no urgency
  • Stale data; failure can go unnoticed
  • Needs monitoring, notification, error recovery
vs

Real-Time

  • Within milliseconds
  • Systems talk through an event stream
  • IoT, trading, live tracking, live inventory
  • Complex, expensive, demands high throughput
  • Needs scalable event processing, consistency guarantees

Terms Glossary

•Data integration pattern — a structured, named approach to transporting, transforming, and combining data
•Data silo — data trapped in one system, in a format other systems can't use
•Migration — one-way, one-time transfer from a source system to a target system
•Filtering criteria — the rules that decide which data a migration will carry
•Transformation — changing data's format or structure so the receiving system can use it
•Transactional — only data changed since the last run is moved
•Reverse ETL — pushing warehouse data back into an operational system such as Salesforce
•Correlation — bi-directional sync performed only on records that exist in both datasets
•Union — all records from both sets; what bi-directional sync covers
•Intersection — only records in both sets; what correlation covers
•ETL / ELT — two ways of doing aggregation
•Data warehouse — the single store that aggregation feeds
•Interface — the direct link built between two systems in point-to-point integration
•Tight coupling — a change in one system forces changes in the systems connected to it
•Integration hub — the central component that routes and transforms between connected systems
•Enterprise Service Bus (ESB) — the classic implementation of an integration hub
•Decoupling — systems don't need knowledge of each other's internals to work together
•Single point of failure — one component whose failure stops everything; the hub's main risk
•Message broker — the middleware that receives published messages and distributes them
•Topic/channel — the named category a message is published to and subscribed from
•Blocking operation — the requesting system stops processing until the response or timeout arrives
•Timeout — the limit on how long a requester will wait before giving up
•Batch processing — handling data in scheduled groups rather than one item at a time
•Data mapping — matching a field in one system's format to the right field in another's
•Event-driven communication — integration triggered by events rather than a schedule or a request
•Throughput — how much data a system can handle in a given time
•Latency — the delay between sending something and it arriving
